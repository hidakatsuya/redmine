# ガント内部刷新の回帰テスト案

最新の[再検証結果（2026-09-10、G01–G21・41ケース）](GANTT_TEST_RESULTS_20260910.md)はこちら。

この文書はテストの計画を定義する。2026-09-08 に G01–G20 を40ケースで実行した
[結果・修正内容・未確認項目](GANTT_TEST_RESULTS.md) と、
[再実行用ツール](../test/gantt_visual/README.md) を別途記録している。
ケースの実行と、人間による見た目の承認・実プリンターの確認は分けて扱う。
目的は origin/master と内部刷新後の意味・操作・出力を比較し、スタイル改善へ進める状態かを人間が判断できるようにすること。

## 比較の単位

ケース定義、データ、操作手順、期待結果は変更前後で共通にする。実装固有の CSS セレクターだけをドライバー側で分ける。
比較元は実行開始時の origin/master の SHA、比較先は SHA と未コミット差分のパッチを保存する。ブランチ名だけを記録しない。

各ケースの定義には ID、目的、データセット、利用者、クエリ、表示期間、ズーム、操作、期待する行・関連・出力、実行対象の出力形式を持たせる。
期待するチケット ID・行順はケースの仕様として独立に定義し、変更後の Dataset から生成しない。
HTML 内の DOM ID は変更可能なので、比較時はプロジェクト ID・表示先プロジェクト ID・バージョン ID・チケット ID で論理的な行を識別する。

## 実行環境を固定する

- 専用の DB スナップショットを両実装へ複製する。開発用 DB を書き換えない。各ケースの開始状態も復元する。
- サーバー側の現在日時をテスト用の仕組みで固定する。表示期間を URL で固定するだけでは、遅延・今日線・進捗線が日々変わる。
- Ruby、bundle、DB、ブラウザ、OS/コンテナ、フォント、PDF レンダラー、ImageMagick のバージョンを固定・記録する。
- タイムゾーン、言語、テーマ、休日設定、開始曜日、ユーザー権限と個人設定を固定する。
- viewport と device scale、ズーム、スクロール位置、印刷設定、背景印刷の有無を明示する。
- フォント・画像・Stimulus の初期化と関連線の描画完了を待つ。固定秒数の sleep のみには依存しない。
- 各チェックアウトでアセットを生成し、他方のアセットやブラウザキャッシュを混在させない。

## 保存する成果物

画面は通常の viewport と、必要なスクロール位置の画像を保存する。全ページスクリーンショットだけでは固定要素や横スクロールの問題を見落とす。
PDF とブラウザ印刷は元の PDF と、固定 DPI で全ページを PNG 化したものを両方保存する。PDF のバイト列は生成日時などで変わるので、それだけで不一致としない。
ブラウザ印刷は Chromium の実際の PDF 出力経路で取得する。print media のエミュレーションだけでは改ページを検証できない。
PNG エクスポートは原寸のまま比較する。大きい画像を縮小して合否判定しない。

```text
run-ID/
  environment.json
  cases.json
  candidate.patch
  expected/G01/screen.png
  expected/G01/export.pdf
  expected/G01/export-page-001.png
  expected/G01/export.png
  expected/G01/print.pdf
  expected/G01/print-page-001.png
  actual/G01/...
  diff/G01/...
  report.html
  results.json
  review.md
```

各ケースは実行成否、HTTP 状態、論理行の ID/順序/件数、画像寸法、PDF ページ数、エラー、差分量、成果物へのリンクを記録する。
欠けた画像やページを比較対象から除外して成功にしない。生成失敗と画像差分は別の結果にする。

## 差分の判定と人間の確認

reg-cli は expected/actual の画像比較と HTML レポート生成に使える。
PDF の生成・画像化、ケース実行、意味の検証、差分が許容できるかの判定は別途行う。
利用バージョンを検証用の lockfile で固定し、Redmine 本体の実行時依存には加えない。

初回は差分を広い閾値で消さず、原寸の前後画像と差分を見て分類する。
画面の数ピクセルの余白・アイコン配置差は理由付きで許容できるが、日付・進捗・表示対象・行順・ページ欠落は許容しない。
PDF/PNG は描画方式を維持しているため、同じ環境では描画画像の一致を原則とする。

| 判定 | 意味 |
|---|---|
| 一致 | 意味の assertion と画像比較が成功 |
| 許容差分 | 意味は一致。人間が理由を確認した配置等の差分 |
| 回帰 | 対象・計算・操作・出力の破損、または許容できない見た目 |
| 未実施/生成失敗 | 成功として集計しない |
| 要確認 | 自動比較では変化を検出したが、人間の判断が未完了 |

人間は一覧から差分のあるケースへ移動し、前後・差分画像、期待結果、担当者の評価を確認する。
review.md にケース ID、観察した差分、判定理由、レビュー担当者、確認日を残す。
「許容差分」は今回の比較に対する判断であり、expected を自動更新して履歴を消さない。
差分ゼロのケースも代表例を確認し、同じ誤った画面を両側で取得していないことを確認する。

## 進め方

まず G01/G02/G05/G13/G17 の小さなセットで、取得・ページ画像化・レポート・判定記録が機能することを確認する。
その後に全ケースへ展開する。ブラウザ固有の印刷ダイアログや実プリンターは、人間が代表ケースを補完する。
機能テストと視覚比較の結果をまとめて内部刷新を確認した後、スタイル改善の変更前として今回の状態を固定する。
性能は別の固定条件で測り、画像取得中の計測値を比較に混ぜない。

参考: [reg-cli の公式 README](https://github.com/reg-viz/reg-cli#usage)

## G21: 列表示時の連続した罫線と全高のリサイズ

2026年6月開始・6か月・zoom 4で、Status / Priority / Assignee / Updated等の追加列を表示する。

- ヘッダー直下の余白と最終行より下の空白でも、件名と各追加列の縦罫線が途切れない。
- 件名と最初の追加列の境界を、ヘッダー・データ行の高さ・下の空白からドラッグできる。
- 追加列の右境界も同じ3か所からリサイズでき、ヘッダー・本文・下部の罫線位置が一致する。
- 新旧とも同じ位置から同じ距離（60px）ドラッグし、幅の増加を検証する。
- 横スクロール、列の非表示→再表示、印刷と画面復帰、狭い画面でも罫線・操作領域が追従する。
- 各操作後の画面とブラウザ印刷PDF、初期状態のPDF/PNG出力を保存し、前後・差分を比較する。

このケースは、ヘッダー内のハンドルだけを操作していたG12を補完する。
